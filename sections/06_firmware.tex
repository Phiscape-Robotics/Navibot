\section{Software Design \& Processing}

\subsection{Raspberry Pi Role and Platform}
The Raspberry Pi 4B (4 GB) is the planned high-level compute and sensing unit. The proposed software platform is ROS 2 Lyrical Luth on 64-bit Ubuntu 26.04 LTS for arm64. ROS 2 lists arm64 Ubuntu 26.04 as a Tier 1 platform, and Ubuntu provides Raspberry Pi images for this release \cite{ros_lyrical_platforms,ubuntu_raspberry_pi}. Confirm the final operating-system image, storage, and power arrangement before deployment.

The Pi handles sensor drivers, high-level behavior, and communication with the motor controllers. It does not perform the motor-level control loop. Each Arduino remains responsible for its two motors, encoder acquisition, and an independent communication watchdog that disables motor output if valid commands from the Pi stop.

\subsection{ROS 2 Software Architecture}
The Pi software is organized as ROS 2 nodes with message topics between sensing, decision-making, and drive control. The initial architecture has the following responsibilities:
\begin{itemize}
    \item \textbf{LiDAR driver:} the YDLIDAR X2 serial unit uses the manufacturer's ROS 2 driver and publishes scans on \texttt{/scan} as \texttt{sensor\_msgs/msg/LaserScan}; mounting alignment and scan performance remain to be verified on the robot.
    \item \textbf{Camera driver:} the Raspberry Pi Camera Module V2 (IMX219) is brought up with the upstream ROS 2 \texttt{camera\_ros} node. It publishes \texttt{/camera/image\_raw} and \texttt{/camera/camera\_info}. The verified output is 640 by 480 pixels in \texttt{bgr8}; calibration and the robot-to-camera transform remain deployment requirements.
    \item \textbf{Motion source:} an operator, teleoperation, or future navigation node publishes four signed wheel RPM targets on \texttt{/motor\_bridge/target\_rpm}. The current bridge is a wheel-level interface, not a \texttt{cmd\_vel} or odometry interface.
    \item \textbf{Motor bridge:} the ROS 2 \texttt{navibot\_motor\_bridge} node owns one USB-to-RS-485 adapter, polls the front and rear controllers sequentially, validates feedback, and publishes wheel measurements and bridge status.
    \item \textbf{Arduino controllers:} two classic Arduino Nano nodes control the front and rear motor pairs. Each runs its local speed PI controllers, acquires encoder feedback, and enforces a command watchdog. The Nanos do not run ROS 2.
\end{itemize}

The YDLIDAR X2 model and ROS 2 driver are identified. Its robot mounting transform, scan alignment, and measurement accuracy still need physical verification. Camera calibration, camera mounting transform, navigation stack, and operator interface remain to be specified. Wheel diameter, track width, and steering geometry are still needed before adding a body-velocity (\texttt{cmd\_vel}) or odometry interface.

\subsection{Pi Camera V2 Bring-up}
The Pi Camera V2 (IMX219) uses the upstream \texttt{camera\_ros} node \cite{camera_ros}. The launch configuration requests 640 by 480 output at approximately 15 frames per second and selects the 1640 by 1232 sensor mode to avoid using a cropped VGA sensor mode. Requested stream settings are not guaranteed: the camera driver may adjust unsupported values, so the actual startup log and resulting image dimensions must be checked on the sensor in use.

On the configured Pi, bring up the camera with the following environment and launch command:
\begin{lstlisting}[language=bash]
~/setup-camera.sh
source /opt/ros/lyrical/setup.bash
source ~/ros2_ws/install/setup.bash
ros2 launch navibot_camera camera.launch.py
\end{lstlisting}

The node publishes \texttt{/camera/image\_raw} and \texttt{/camera/camera\_info}. Both use the image frame \texttt{camera\_optical\_frame}, with axes x right, y down, and z forward. The transform from this optical frame to the robot frame must be calculated from the measured camera mounting position and orientation; it is not supplied by the camera package and must not be guessed.

The camera starts uncalibrated. Supply measured calibration data through the launch argument:
\begin{lstlisting}[language=bash]
ros2 launch navibot_camera camera.launch.py camera_info_url:=file:///absolute/path/calibration.yaml
\end{lstlisting}
Do not use zero-initialized camera intrinsics for geometry or image rectification. Image compression is available only if a compatible \texttt{image\_transport} plugin is installed; compressed topics are not guaranteed by this package.

\subsubsection{Pi 4 libcamera runtime workaround}
On the validated Pi 4 installation, ROS libcamera 0.7.2 enumerates the camera but its isolated IPA helper aborts with \texttt{A list of V4L2 controls requires a ControlInfoMap}. Standalone capture and ROS streaming work with Ubuntu libcamera 0.7.0. For this installation, the launch file preloads Ubuntu's matching libcamera libraries and selects the corresponding IPA modules and proxy, scoped to the camera process and its children. Both package versions remain installed; no global library paths are changed. This workaround is specific to this Ubuntu ARM64 installation and must be reviewed after libcamera upgrades.

If the camera is not detected, \texttt{cam -l} should list the IMX219. Devices such as \texttt{/dev/video10} alone may be ISP or codec interfaces and do not establish that a sensor is connected. The current boot configuration has \texttt{camera\_auto\_detect=1}. Before inspecting the CSI connection, shut the Pi down and disconnect power; do not reconnect the ribbon cable while powered. Reboot and check \texttt{cam -l} after reseating the cable.

\subsubsection{Camera verification and limits}
Streaming can be checked from a second terminal after sourcing both ROS environments:
\begin{lstlisting}[language=bash]
ros2 topic hz /camera/image_raw --qos-reliability best_effort
ros2 topic echo /camera/camera_info --once --qos-reliability best_effort
\end{lstlisting}
The saved launch configuration has delivered 60 image messages and 60 CameraInfo messages at approximately 15 FPS on the Pi. The verified image encoding is \texttt{bgr8}, 640 by 480, with 921600 bytes per frame. CameraInfo remains uncalibrated; zero dimensions and intrinsics are expected until calibration data is supplied. A stream-adjustment warning is acceptable only when the resulting dimensions and encoding match the intended output. A successful build by itself does not validate the external \texttt{camera\_ros} executable, libcamera compatibility, physical sensor, stream, or calibration.

For a graphical preview, run \texttt{rqt\_image\_view} on a computer with ROS 2 and a desktop, then select \texttt{/camera/image\_raw}. Remote viewing requires working ROS discovery and matching \texttt{ROS\_DOMAIN\_ID} values between the computer and Pi. A remote terminal does not itself provide a graphical display; this camera setup does not include a browser-based viewer.

\subsection{Motor Bridge and Wheel Interfaces}
The Pi runs the ROS 2 package \texttt{navibot\_motor\_bridge} as the RS-485 bus master. A single shared half-duplex RS-485 bus links the Pi's USB-to-RS-485 adapter to both motor-controller boards. The front Nano has address 1 and controls front-left/front-right; the rear Nano has address 2 and controls rear-left/rear-right. Both Nanos perform their own wheel-speed PI control locally. The Pi is the only bus master: it polls one addressed Nano at a time, and only that Nano replies, preventing simultaneous node transmissions. The serial link carries target RPM and returns measured RPM, applied duty, status flags, and sample timing. The Nano firmware and wire protocol are not yet implemented; the proposed wire contract is specified below for implementation in the Pi bridge and both Nano nodes.

The configured transport is 115200 baud, 8 data bits, no parity, and 1 stop bit (8N1), with node addresses 1 (front) and 2 (rear). Each poll/response exchange is one bus transaction; the bridge schedules 50 transactions per second total, alternating between nodes. The proposed frame design below carries the addressed node's two signed wheel-speed targets and returns that node's measured RPM, applied duty, status flags, and sample age. Firmware implementation and physical bus validation are pending. Termination, biasing, signal reference, and adapter turnaround must be verified against the selected transceivers and USB adapter before physical operation \cite{ti_rs485}.

\subsubsection{Proposed RS-485 Frame Design}
This is the design target for the Pi bridge and both Nano firmware nodes; it is not yet implemented. The Pi sends one request at a time and waits for a matching reply before polling the other node. All multi-byte values are little-endian. No node transmits unless it receives a valid request addressed to its node ID.

The bridge should increment the sequence for each new poll and accept a reply only when its version, address, type, sequence, length, and CRC match the outstanding request. A controller should validate the complete request before applying either wheel target, then reply with the same address and sequence. Invalid sync, version, address, type, length, or CRC frames must be discarded without changing targets or refreshing the watchdog. A valid command refreshes the controller's 250 ms command watchdog; if it expires, both motor outputs are set to zero. The bridge uses a 12 ms reply timeout, discards late or mismatched replies, and continues polling the other node. There are no broadcast commands. The parser must recover by scanning for the sync bytes after a malformed frame; because the length is explicit and CRC checked, payload bytes do not require escaping.

Positive RPM is defined as the calibrated forward direction for each wheel. Firmware must apply the configured sign correction for motors whose wiring makes positive duty rotate in reverse. Any change to byte fields, scaling, status bits, or CRC parameters requires a protocol-version increment.

The target ROS message is \texttt{std\_msgs/msg/Float64MultiArray} on \texttt{/motor\_bridge/target\_rpm}, ordered front-left, front-right, rear-left, rear-right. Values are signed RPM, initially limited to $\pm135$ RPM. The publisher must send targets repeatedly; a command expires after 250 ms. Invalid target arrays request zero. The feedback topics are \texttt{/motor\_bridge/wheel\_rpm} and \texttt{/motor\_bridge/wheel\_duty}, also ordered by wheel. Disconnected or stale measurements are reported as NaN. Duty is a signed percentage from $-100$ to $+100$. The \texttt{/motor\_bridge/status} topic is a \texttt{std\_msgs/msg/String} that reports feedback freshness, Nano status flags, and sample times.

At 50 transactions per second total, each Nano is polled at approximately 25 Hz; ROS feedback topics publish at 5 Hz. Each wheel value is the latest received value from its controller. Since the two Nanos are polled independently, a four-wheel message is not a synchronized snapshot. The interface does not yet convert \texttt{cmd\_vel} to wheel commands or calculate odometry; wheel diameter, track width, and steering geometry are not yet defined.

\subsection{Motor Bridge Safety and Fault Handling}
The bridge opens the port exclusively, starts with zero targets, and retries an unavailable adapter every two seconds. It accepts nonzero targets only when both controllers have fresh feedback and neither reports RPM-invalid or controller-fault flags. If communication health is lost, targets are inhibited until the health checks pass again and a fresh ROS target command arrives. Stop packets are attempted during orderly shutdown, but packet delivery cannot be relied upon after Pi, cable, or adapter failure. Each Nano must independently force PWM off after 250 ms without a valid addressed command.

For an initial motor test, all four wheels must be lifted clear and a motor-power stop must be available. Test only after the two Nanos implement the same protocol and watchdog in \texttt{PROTOCOL.md}. Do not run another serial application against the adapter concurrently.

The ROS status topic can be inspected in one sourced terminal while a brief low-speed command is published from another:
\begin{lstlisting}[language=bash]
ros2 topic echo /motor_bridge/status
ros2 topic pub -r 10 /motor_bridge/target_rpm std_msgs/msg/Float64MultiArray '{data: [10.0, 10.0, 10.0, 10.0]}'
\end{lstlisting}
Stop the publisher with Ctrl-C; the bridge lets the command expire and requests zero targets. This procedure is only for the controlled, wheels-raised test described above.

\paragraph{Troubleshooting.}
For a missing device, check \texttt{/dev/serial/by-id/} and \texttt{/dev/ttyUSB*}; for permission errors, check \texttt{dialout} membership and start a new login after group changes. Do not make the device world-writable. A busy port indicates another serial process must be stopped. NaN feedback or stale status calls for checking Nano addresses, firmware, baud rate, wiring, CRC handling, and adapter direction switching. Zero targets call for checking the four-element order, RPM bounds, repeated publication, and both Nano status flags.

The transform from \texttt{base\_link} to \texttt{laser\_frame} must be calculated from measured mounting geometry; this driver does not publish a guessed robot transform. Check forward-angle alignment against stationary objects after mounting.

\subsubsection{Driver revisions and validation}
The Pi workspace uses YDLIDAR SDK commit \texttt{42a82ed10d2304094c111fc63dee8e4a229b79b7} and the \texttt{humble} branch of \texttt{ydlidar\_ros2\_driver} at commit \texttt{4ef70d3f32a85704ade0be54b214f3763b1ab3e8}. The driver settings follow the manufacturer's configuration reference \cite{ydlidar_config}. Both packages built on the Pi under ROS 2 Lyrical after the local compatibility patches. In a bounded live capture, 30 scans arrived at approximately 11.58 Hz with 260 samples per scan; the last scan contained 177 finite in-range returns from 0.195 m to 7.155 m, with frame \texttt{laser\_frame} and configured limits of 0.1--8.0 m. This confirms streaming on that setup, not ranging accuracy or calibration. The measured scan rate exceeded the requested 6 Hz; actual rate depends on the sensor motor and hardware, so the requested frequency must not be treated as a guaranteed output rate.

During initialization the SDK logged \texttt{Fail to get baseplate device information!}, followed by successful initialization and scan streaming. The warning did not prevent that capture; investigate it if scan startup or continuity fails. If the adapter is missing, inspect \texttt{/dev/serial/by-id/} and \texttt{/dev/serial/by-path/}. For permission errors, check \texttt{dialout} membership (the Pi's \texttt{rpi} account is already a member). If scans are absent, check exclusive port ownership, sensor rotation, baud rate, and single-channel configuration. Compare stationary objects at known distances to investigate unexpected ranges or angles. The robot transform, forward-angle alignment, and measurement accuracy remain unverified.

\subsection{Pi Software Validation Status}
The motor bridge's pseudo-terminal integration tests have passed with two simulated Nanos, covering signed commands to both addresses, fragmented replies, bad checksums, wrong sequences, command expiry, feedback loss and recovery, and shutdown zero commands. These tests exercise the existing bridge behavior with simulated serial peers; they do not establish implementation or interoperability of the proposed frame design above. The installed launch command was checked with the adapter absent. USB-RS-485 turnaround, bus wiring, Nano firmware, encoder calibration, and physical motor response remain unverified. The camera streaming results are recorded in the camera subsection above. The repository's \texttt{tools/scan\_wifi\_devices.py} remains a separate network-discovery utility; its role in the robot is unspecified.
